# راه‌اندازی کمپین، مسیر تعاملی و چت

## تأیید مشتری در سفارش و پرتال

اتصال واقعی ملی‌پیامک اضافه شده است: `ENABLE_MELIPAYAMAK_OTP=true`، توکن محرمانه در `MELIPAYAMAK_OTP_TOKEN` و کلید HMAC ثابت ۳۲بایتی به شکل ۶۴ کاراکتر hex در `OTP_HASH_SECRET` تنظیم می‌شوند. در این حالت، گزینهٔ پیامک در سفارش/پرتال فعال و کد ثابت حتی در localhost رد می‌شود. endpoint فقط در سرور و با origin/path ثابت فراخوانی می‌شود؛ پاسخ حاوی کد به کلاینت/لاگ نمی‌رود. فعلاً خود سرویس با همان توکن HTTP 400 و «مستلزم تنظیم و تأیید مدیر» می‌دهد؛ تأیید/فعال‌سازی OTP در کنسول ملی‌پیامک لازم است. تست دارای شماره واقعی فقط با اجازه صریح انجام می‌شود، به‌طور خودکار تکرار نمی‌شود و تحویل موفق در این مرحله تأیید نشده است.

کد ۵ دقیقه، حداکثر ۵ تلاش و یک بار مصرف دارد. ارسال مجدد ۶۰ ثانیه فاصله و برای شماره و مرورگر سقف ۵ در ساعت دارد؛ سقف سراسری ۲۰۰ در ساعت است. ارسال ابتدا در Supabase claim می‌شود و hash کد به مرورگر/challenge وابسته است. تماس تأییدشده ۳۰ دقیقه برای همان اطلاعات معتبر و برای ساخت حساب یک بار قابل استفاده است. رکوردهای ارسال بیش از ۲۴ ساعت، در دسته‌های حداکثر ۱۰۰تایی هنگام درخواست جدید پاک می‌شوند؛ پاک‌سازی زمان‌بندی‌شده اضافه نشده است.

با توجه به خاموش بودن Hosted Phone Auth، حساب موبایلی واقعی شناسه تصادفی داخلی `@phone-login.invalid` و شماره تأییدشده دارد و از رمز/session خود Supabase استفاده می‌کند. ورود با موبایل از نگاشت server-only به شناسه داخلی انجام می‌شود. ایمیل فرم تأیید نمی‌شود؛ مدارک و عضویت staff برای این شناسه در API و RLS مسدودند. مسیر تأیید ایمیل پرونده مستقل می‌ماند. توضیحات کد ثابت در ادامه صرفاً برای demo محلی با flag واقعی خاموش است.

بعد از چهار فیلد سفارش، تماس جدید باید با ایمیل یا پیامک واقعی (یا در demo با تست موبایل) تأیید شود. وجود ایمیل یا موبایل در CRM، سفارش‌ها یا حساب تأییدشده، مرحلهٔ تماس سفارش را حذف می‌کند؛ این وضعیت فقط ثبت سفارش را مجاز می‌کند و اجازهٔ ورود/ادغام/خواندن پرونده نیست. حساب Auth تأییدنشده به‌تنهایی راه دورزدن نیست. trigger سفارش، شرط را مستقل از رابط اجرا و روش `email`، `mobile`، `test_phone` یا `existing` را در `contact_check` ثبت می‌کند.

برای آزمایش محلی `ENABLE_TEST_OTP=true` و کد `123456` است؛ ارقام فارسی/عربی هم پذیرفته می‌شوند. در production HTTP محلی، `BACKOFFICE_LOCAL_HTTP=true` هم لازم است. origin عمومی حتی با flag روشن این کد را نمی‌پذیرد؛ پیش‌فرض `.env.example` خاموش است. این مرحله هیچ SMS نمی‌فرستد و مالکیت واقعی تماس را ثابت نمی‌کند. challenge ده دقیقه، پنج تلاش و نتیجه سی دقیقه اعتبار دارد؛ تغییر جفت ایمیل/موبایل یا مرورگر آن را منتقل نمی‌کند. رکوردهای منقضی هنگام شروع بررسی جدید در دسته‌های ۱۰۰تایی حذف می‌شوند؛ job زمان‌بندی اضافه نشده است.

پرتال `/portal` ثبت‌نام با نام/نام خانوادگی/ایمیل/موبایل/رمز و انتخاب روش تأیید دارد. حساب موجود با ایمیل یا موبایل و رمز وارد می‌شود. ایمیل واقعی از `auth.signUp` و تأیید لینک استفاده می‌کند؛ در سفارش `signInWithOtp` لینک می‌فرستد و callback مجاز `/auth/callback?next=registration` تماس همان مرورگر را بازیابی می‌کند. دامنه و redirectهای مجاز و SMTP باید برای میزبان واقعی پیکربندی شوند؛ ارسال واقعی ایمیل در QA اجرا نمی‌شود.

چون Phone Auth پروژه فعلاً خاموش است، تست موبایل از حساب Supabase با شناسهٔ تصادفی داخلی `@local-otp.invalid` استفاده می‌کند. این شناسه ایمیل مشتری نیست و هیچ ایمیلی به آن فرستاده نمی‌شود. موبایل به همان Auth ID ذخیره و ورود با رمز از نگاشت service-only انجام می‌شود. ایمیل مشتری صرفاً `user_metadata.claimed_email` است و در دسترسی استفاده نمی‌شود. policy محدودکنندهٔ RLS و guardهای API، حساب داخلی را از مدارک/Storage/مدیریت محروم می‌کنند، حتی اگر دعوتی اشتباه به شناسهٔ آن ثبت شود. بعداً تأیید واقعی ایمیل با magic link هویت جداگانه دارای ایمیل واقعی را برقرار می‌کند؛ رمز آزمایشی به آن منتقل نمی‌شود. این مسیر جای اتصال Phone Auth/OTP واقعی را نمی‌گیرد.

برای اجرای `scripts/qa-growth-live.ts` علاوه بر تنظیمات قبلی، flag محلی تست OTP هم روشن باشد. harness حساب آزمایشی ثبت‌نام، ورود مجدد، رد کد اشتباه و منع مدارک/پنل را با Supabase واقعی بررسی و حساب‌ها/بررسی‌های همان اجرا را پاک می‌کند؛ هیچ ایمیل یا SMS آزمایشی خارجی ارسال نمی‌شود.

## لید و اعلان پشتیبانی

پیش از اولین پیام انسانی، فرم سه‌فیلدی نام، نام خانوادگی و موبایل در چت نمایش داده می‌شود. اعتبارسنجی سمت سرور و شرط داخل تراکنش SQL اجازه دورزدن فرم را نمی‌دهند. ارقام فارسی/عربی و پیش‌شماره ایران نرمال می‌شوند؛ موبایل صرفاً اعلام‌شده است و تأیید پیامکی ندارد. هر گفت‌وگو لید خودش را دارد؛ شماره مشترک گفت‌وگوها را ادغام نمی‌کند. کارشناس در `/backoffice/chat` نام و لینک تماس را می‌بیند. گفت‌وگوهای قدیمی حفظ می‌شوند؛ مشتری پیش از پیام بعدی اطلاعات تماس را کامل می‌کند.

اعلان‌ها داخل سایت‌اند. پاسخ کارشناس در دکمهٔ بستهٔ چت شمارنده دارد و پس از reload نیز باقی می‌ماند. بازکردن چت در تب قابل مشاهده، فقط پاسخ‌های نمایش‌داده‌شده را خوانده‌شده می‌کند؛ دکمهٔ علامت‌گذاری همه برای موارد قدیمی هم موجود است. اعلان کارشناس در زنگ بالای تمام صفحات بک‌آفیس، با ۲۰ مورد آخر و لینک مستقیم به گفت‌وگوست. وضعیت هر کارشناس در `growth_chat_reads` مستقل است؛ بستن toast وضعیت خواندن را تغییر نمی‌دهد. هیچ متن پیام یا موبایلی در toast قرار نمی‌گیرد.

Migration `chat_leads_notifications` ستون‌های تماس، رسید خواندن مشتری، جدول رسید هر کارشناس و RPCهای محدودشده را اضافه می‌کند. `growth_chat_inbox` با `security_invoker` و RLS اجرا می‌شود. RPC مهمان فقط از سرور با کوکی HttpOnly فراخوانی می‌شود؛ مشتری یا anon دسترسی مستقیم به لیدها و رسیدها ندارند. نام/موبایل/متن پیام وارد analytics یا localStorage نمی‌شوند. متن seed حریم خصوصی فقط در صورت دست‌نخوردن توسط مدیر به‌روزرسانی می‌شود.

به‌روزرسانی در تب قابل مشاهده با polling چندثانیه‌ای انجام می‌شود؛ Web Push، SMS، صدا و اعلان سیستم‌عامل اضافه نشده‌اند. این قابلیت برای چت مشتری/کارشناس است؛ یادداشت‌های داخلی پرونده به مشتری نمایش داده نمی‌شوند. پاک‌کردن کوکی یا استفاده از مرورگر دیگر قابلیت دسترسی مهمان را بازیابی نمی‌کند.

## مشاهده بدون حساب واقعی

```bash
npm ci
npm run demo
```

- وب‌سایت: `http://127.0.0.1:3000`
- پنل: `http://127.0.0.1:3000/backoffice/login`
- کاربر **صرفاً مصنوعی دمو**: `growth-staff@example.invalid`
- رمز **صرفاً مصنوعی دمو**: `synthetic-password`
- کدهای آماده: `TEST100` و `TEST50`. کمپین جدید را از `/backoffice/campaigns` بسازید.
- یک پنجره سایت و پنجره دیگر بک‌آفیس باز کنید؛ پیام مشتری را از `/backoffice/chat` پاسخ دهید.

دمو روی loopback و دیتابیس PostgreSQL حافظه‌ای اجرا می‌شود؛ با توقف تمام داده‌ها حذف می‌شوند. هیچ credential واقعی، پیامک، ایمیل، درگاه یا مدرک واقعی در این حالت استفاده نشود. این backend فقط ابزار بازبینی/تست است، در برنامه production فراخوانی نمی‌شود. برای استفاده روی میزبان خارجی آن را منتشر نکنید. دو پورت ۳۰۰۰ و ۳۳۰۱ لازم است؛ Ctrl+C هر دو را می‌بندد.

## اتصال به پروژه Supabase

۱. migrationهای قبلی و سپس `20261024052205_growth.sql` و `20261024052214_growth_copy.sql` را با فرایند migration پروژه اعمال کنید. این migrationها در 2026-10-24 روی پروژه Supabase اعمال شدند و نام فایل‌ها با تاریخچه واقعی یکسان است. migration دوم فقط متن seed دست‌نخورده را به‌روز می‌کند و محتوای سفارشی مدیر را حفظ می‌کند.
۲. `SUPABASE_URL`، `SUPABASE_PUBLISHABLE_KEY` و `SUPABASE_SECRET_KEY` را در تنظیمات محرمانه سرور قرار دهید؛ `SUPABASE_SERVICE_ROLE_KEY` قدیمی فقط fallback است. نام هیچ کلید خصوصی نباید با `NEXT_PUBLIC_` شروع شود. کلید سرور فقط در API عمومی server و برای capability مهمان استفاده می‌شود؛ پنل از JWT کاربر و RLS استفاده می‌کند. helper بررسی UID و ایمیل تأییدشده در schema غیرعمومی `growth_private` است؛ RPCهای سفارش، تکمیل و چت SECURITY INVOKER هستند و به service_role محدودند. پاسخ کارشناس با JWT و سیاست‌های نوشتن مخصوص کارشناس اعمال می‌شود.
۳. کاربر را از `/backoffice/users` اضافه و بخش‌های مجاز را تعیین کنید. ایمیل حساب تأییدشده باید عضویت فعال و مجوز همان بخش را در `cms_editors` داشته باشد. ساخت حساب، مجوز مدیریت نمی‌دهد. UID واقعی `auth.users`، تأیید ایمیل و مجوز فعلی دیتابیس هم‌زمان بررسی می‌شوند؛ غیرفعال‌سازی روی همان نشست باز هم اثر دارد. مالک و تغییر دسترسی خود مدیر محافظت شده‌اند.
۴. برای شبیه‌ساز پایدار روی Supabase: `COMMERCE_MODE=simulation` و `ENABLE_CHECKOUT=false`. کمپین از همان نوع `simulation` بسازید. محیط کمپین و سفارش باید یکسان باشد.
۵. برای ثبت سفارش واقعی بدون درگاه: `COMMERCE_MODE=live` و `ENABLE_CHECKOUT=false`. فرم سفارش را ذخیره می‌کند و کد پیگیری می‌دهد؛ سفارش دارای مانده pending/پرداخت‌نشده می‌ماند و پرونده خدماتی یا رسید بانکی تولید نمی‌کند. تخفیف صددرصد در همین حالت یک پرونده واقعی با دریافت مدارک بسته ایجاد می‌کند. کمپین را با محیط «واقعی» بسازید؛ این محیط در پنل متناسب با محیط فعلی پیش‌فرض می‌شود. برای فعال‌سازی بعدی sandbox یا درگاه واقعی، علاوه بر mode مربوط، `ENABLE_CHECKOUT=true`، merchant معتبر، `SITE_URL` با HTTPS و callback مجاز لازم‌اند؛ ابتدا قیمت/اقلام/لغو/حریم خصوصی نهایی و آزمایش کنترل‌شده انجام شوند. نبود flag صریح حتی با merchant موجود درگاه را می‌بندد. `BACKOFFICE_LOCAL_HTTP` روی میزبان HTTPS خاموش بماند.
۶. در Supabase Auth، تأیید ایمیل فعال و URL `/auth/callback` دامنه در Redirect URLs مجاز باشد. لینک PKCE در مرورگر شروع‌کننده باز می‌شود؛ پس از تأیید ایمیل می‌توان با رمز در مرورگر دیگر وارد شد. SMTP و محدودیت ارسال باید جدا آزمایش شوند.

## مدل داده و وضعیت‌ها

- `growth_campaigns`: نام/کد یکتا، درصد صحیح ۱–۱۰۰، سقف استفاده، زمان شروع/پایان، خدمت، محیط، کانال و توضیح. پس از ایجاد فقط active قابل تغییر است؛ شرایط تاریخی تغییر نمی‌کنند.
- `growth_orders`: چهار فیلد، مبلغ پایه/تخفیف/نهایی به تومان، شناسه تلاش، hash ورودی و capability، محیط، وضعیت پرداخت و ارجاع پرونده. hash capability غیرقابل استفاده به جای cookie خام است.
- قیمت‌ها در `site.ts` و قرارداد SQL ثبت شده‌اند؛ تغییر قیمت مستلزم migration هماهنگ و تست مقدار snapshot است. مرورگر مبلغ را تعیین نمی‌کند. `expectedTotal` فقط رضایت با آخرین مبلغ نمایش‌داده‌شده را کنترل می‌کند.
- رزرو با قفل مهمان، تلاش و کمپین انجام می‌شود. تکمیل نیز قفل همان کمپین را می‌گیرد تا مرز انقضای آخرین ظرفیت باعث oversell نشود. یک کد برای یک ایمیل نرمال‌شده یک بار؛ این به معنی تشخیص یک انسان با ایمیل‌های متفاوت نیست.
- سفارش شبیه‌ساز در ۲۰ دقیقه منقضی می‌شود. رزرو پرداخت خارجی خودکار آزاد نمی‌شود، چون بستن مرورگر به معنی عدم پرداخت نیست. سفارش‌های initiating/redirected نامعلوم باید با پنل زرین‌پال تطبیق داده شوند؛ آزادسازی دستی بدون بررسی بانکی پیاده نشده است.
- تخفیف کامل `payment_kind=discount` است. در شبیه‌ساز هیچ CRM ساخته نمی‌شود. در محیط واقعی یک مشتری مستقل و پرونده با دریافت مدارک بسته ساخته می‌شود؛ سفارش با ایمیل ادعایی به رکورد مشتری قبلی متصل نمی‌شود.
- رسید دستی، اعتبار تخفیف و مبلغ درگاه در خلاصه مالی جدا هستند. وضعیت مالی هرگز وضعیت بررسی مدارک یا ثبت رسمی DV را تغییر نمی‌دهد.
- `growth_conversations` و `growth_messages`: چت مهمان و پاسخ کارشناس؛ مستقل از `crm_ticket_messages` که یادداشت داخلی است. کوکی مهمان HttpOnly با طول ۲۵۶بیت و عمر ۳۰روز است. دسترسی چت/سفارش به همان مرورگر وابسته است؛ پرتال مدارک با Supabase Auth کار می‌کند.
- polling چت هر ۴ ثانیه، فقط در پنجره باز و تب فعال، با backoff خطا و سقف ۱۰۰ پیام است؛ صف پنل ۲۵تایی و هر ۵ثانیه به‌روز می‌شود. ایندکس‌های conversation/time و queue/time برقرارند. در مقیاس بزرگ‌تر می‌توان پس از سنجش بار به Realtime خصوصی مهاجرت کرد؛ حضور آنلاین اپراتور ادعا نمی‌شود.
- محدودسازی درخواست DB-backed است. کوکی جدید هم سقف کلی دارد؛ WAF/محدودیت لبه میزبان برای حمله توزیع‌شده همچنان لازم است. کلیدهای rate limit قدیمی به‌صورت دسته‌های کوچک پاک می‌شوند. سیاست نهایی نگهداری پیام و سفارش پیش از استفاده عملیاتی باید تعیین شود؛ حذف خودکار این سوابق فعال نیست.

## تست و حدود شواهد

```bash
npm test
npm run lint
npm run typecheck
npm run build
npm run test:e2e
npm run test:growth
```

`test:growth` مسیر واقعی React → Next API → HTTP test double → همان migrationهای PostgreSQL را اجرا می‌کند. رابط Auth/PostgREST مصنوعی است؛ مدرک سازگاری کامل یا دسترسی زنده Supabase محسوب نمی‌شود. PGlite تک‌اتصالی است و جای آزمایش contention با چند اتصال واقعی Postgres را نمی‌گیرد. قرارداد درگاه با fetch مصنوعی تست شده؛ sandbox و پرداخت زنده، SMTP، پیامک و بار چندکاربره میزبانی‌شده در این محیط آزمایش نشده‌اند.

آزمون صریح اتصال واقعی بدون درگاه: پس از build، یک سرور جدا با تنظیمات واقعی `.env.local`، `COMMERCE_MODE=live`، `ENABLE_CHECKOUT=false` و برای HTTP محلی `BACKOFFICE_LOCAL_HTTP=true` روی پورت 3200 اجرا کنید؛ سپس `node --env-file=.env.local --import tsx scripts/qa-growth-live.ts`. این harness با Auth Admin یک حساب مصنوعی بدون ارسال ایمیل می‌سازد، سفارش و کمپین و چت واقعی را با داده مصنوعی تست و رکوردها/حساب همان تست را پاک می‌کند. کلید یا اطلاعات واقعی مشتری در fixture قرار نمی‌گیرد. دامنه این harness فقط localhost است؛ `QA_ORIGIN` برای تغییر پورت محلی است. تست‌ها و `npm run demo` کلیدهای واقعی را override می‌کنند تا `.env.local` موجب اتصال تصادفی آن‌ها به دیتابیس واقعی نشود.

قبل از انتشار: تنظیمات و migration واقعی، تست cross-account/RLS روی Supabase staging، رقابت چند اتصال برای آخرین ظرفیت، تست sandbox زرین‌پال و callback تکراری، SMTP/تأیید ایمیل، سیاست نگهداری چت/سفارش و شرایط لغو باید بررسی شوند. پروژه در این تسک deploy نشده است.
